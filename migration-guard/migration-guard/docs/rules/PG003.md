# PG003: rename column or table

## What it detects

- `ALTER TABLE ... RENAME COLUMN old TO new`.
- `ALTER TABLE ... RENAME TO new`.

The parser handles schema-qualified and quoted identifiers. Comments and
strings are not treated as statements.

## Why it is risky

The database rename can succeed while old application instances continue to
query the old name during a rolling deployment. Views, functions, triggers,
and other dependants may also reference the old object. The exact lock and
dependency outcome depends on the PostgreSQL version and object graph; this
syntax-only rule therefore describes application compatibility risk rather than
claiming a universal outage.

See PostgreSQL's [ALTER TABLE documentation](https://www.postgresql.org/docs/current/sql-altertable.html)
and [dependency tracking](https://www.postgresql.org/docs/current/ddl-depend.html).

## When it is not necessarily risky

- All application instances are stopped or are deployed atomically.
- Schema replay and application analysis prove there are no remaining old-name
  references.
- The object is test-only or newly created in the same change.

## Severity

PG003 is `high` by default because a rolling deployment commonly has both old
and new application versions active. Schema and application context may lower
confidence, but unknown references must not be treated as safe.

## Safer alternative

For a column, add the new column, dual-write, backfill, switch reads, deploy
the new application, then remove the old column later. For a table, introduce
a compatibility view or dual-write path, migrate consumers, and rename/remove
only after the old consumers are gone.

## Limitations

This rule does not yet inspect application code, views, functions, triggers, or
schema history. It cannot determine deploy order or whether old binaries are
still running.

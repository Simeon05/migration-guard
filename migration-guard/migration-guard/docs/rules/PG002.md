# PG002: destructive table and schema operations

## What it detects

- `DROP TABLE`, including `IF EXISTS`, multiple tables, and `CASCADE`.
- `TRUNCATE`, including `TABLE`, `ONLY`, `RESTART IDENTITY`, and `CASCADE`.
- `DROP SCHEMA`, including `IF EXISTS` and `CASCADE`.

Comments and string or dollar-quoted contents are ignored by the parser.

## Why it is risky

`DROP TABLE` removes the table and its indexes, rules, triggers, and
constraints. `CASCADE` can remove dependent objects recursively. PostgreSQL
acquires `ACCESS EXCLUSIVE` for `DROP TABLE` and `TRUNCATE`; that lock conflicts
with all table lock modes and blocks ordinary reads. `TRUNCATE` removes rows
without scanning the table and does not fire `ON DELETE` triggers.

References: [DROP TABLE](https://www.postgresql.org/docs/current/sql-droptable.html),
[TRUNCATE](https://www.postgresql.org/docs/current/sql-truncate.html),
[DROP SCHEMA](https://www.postgresql.org/docs/current/sql-dropschema.html), and
[table-level locks](https://www.postgresql.org/docs/current/explicit-locking.html).

These semantics are version-sensitive and must be re-verified for each
supported PostgreSQL major version. The current rule is deliberately
conservative and reports the operation as high severity.

## When it is not necessarily risky

- The object is a disposable test or temporary environment object.
- Schema replay proves the table or schema was created only in the current
  change and contains no production data.
- The operation is explicitly approved as part of a reviewed decommissioning
  plan.

`IF EXISTS` only makes retries idempotent; it does not make a successful drop
safe. `RESTRICT` prevents dependency removal but does not protect the data or
avoid the lock.

## Severity

PG002 is `high` by default because it is destructive and may acquire
`ACCESS EXCLUSIVE`. Future schema and hints context may lower confidence or
change severity for objects proven empty or disposable; it must not silently
turn an unknown object into a safe result.

## Safer alternatives

For a table, remove application references, deploy the compatible application,
rename or quarantine the table, wait through the rollback window, and only then
drop it. For truncation where concurrent access matters, use a controlled,
batched `DELETE` with an explicit predicate and operational monitoring.

Avoid `CASCADE` unless the dependent-object list has been reviewed. Run the
operation separately with an appropriate `lock_timeout` and rollback plan.

## Limitations

This syntax-only rule cannot know row counts, application references, object
ownership, transaction duration, or dependencies without schema replay and
application indexing. It does not currently distinguish temporary tables or
test-only migrations.
